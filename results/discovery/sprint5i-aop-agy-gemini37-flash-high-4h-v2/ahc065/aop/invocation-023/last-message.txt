# Progression summary

Can we design a conveyor belt network and move scheduler to extract all 400 boxes from a 20x20 grid in strictly increasing order with the fewest possible conveyor rotations?

I improved the public benchmark score from the 2,500 starter baseline to 276,767,693 points on the native 50-case evaluation suite. Across 50 public seeds, the average operation count per instance dropped to 4,315 rotations while successfully clearing all 400 boxes in 100% of cases.

The solution was evaluated using the official ARS submit command and local judge on seeds 0 through 49.

# Methodology

The algorithm consists of two core components: static conveyor topology design and dynamic move sequence search.

For the static layout, the 20x20 grid is partitioned into 20 closed conveyor loops of length 40:
- 10 horizontal loops (H_0 to H_9), where loop H_k spans row 2k and row 2k+1 across all 20 columns.
- 10 vertical loops (V_0 to V_9), where loop V_j spans column 2j and column 2j+1 across all 20 rows.

This layout satisfies the problem constraints because every cell on the grid belongs to exactly one horizontal loop and one vertical loop, achieving the maximum allowable cell degree of 2. The warehouse exit at cell (0, 10) is part of horizontal highway H_0 (rows 0 and 1) and vertical highway V_5 (columns 10 and 11). Every cell on the board shares 4 intersection points with V_5 via its horizontal loop and 4 intersection points with H_0 via its vertical loop.

For dynamic scheduling, the solver executes an optimized beam search over board states:
- A precomputed distance table `cell_dist[r][c]` stores the exact shortest number of operations needed for any single cell to reach (0, 10).
- Candidate moves include single-target routing via V_5 or H_0, as well as 2-target chained actions where target `t` and target `t+1` are aligned onto highway V_5 or H_0 before executing a combined highway sweep.
- Non-exit conveyor rotations run in O(L) using fast block array permutations, while highway rotations check intermediate exit clearances.
- State history is stored in a zero-allocation global parent-pointer tree pool, eliminating heap memory allocations during search expansions.
- States are evaluated by combining accumulated operations with a discounted lookahead over the next 10 target boxes: `eval = operations + sum_{w=0..9} (0.75^w * cell_dist[pos[target + w]])`.
- Duplicate configurations are pruned using 64-bit state hashing.
- Beam width adjusts dynamically from 35 down to 8 based on elapsed execution time to fit within the 2.0-second limit.

# Caveats

The beam search uses 2-target chained alignments with a 10-step discounted lookahead. Deeper 3-target chains constrain intermediate states too early, displacing downstream targets and increasing total operations compared to flexible 2-target lookahead planning.

# Scoring

For instances where all 400 boxes are removed (B = 400), each test case receives:
`Score = 1,000,000 + round(1,000,000 * log2(100,000 / T))`

When B < 400, the score is `round(1,000,000 * B / 400)`.
